# A policy file may name a single tool: the build check corrected

27 November 2026 · branch `wp4-benchmark-v2` · requirements revision 3.16 (WP3), found by Prof. Koubaa on 26 November 2026.

## What failed

`mcl build` of `enterprise-v2-guarded` stopped with

```
gateway.policy: unknown servers ['ticketing/reply_ticket']
```

for every policy file that did not replace the default sinks with a list of servers:

- a policy file that sets no sinks of its own, which is what the policy file of a guard plugin
  looks like (keys of its own, no lists);
- a policy file that sets nothing, with the lab's own guard;
- a policy file that lists the tool among its sinks, which is how a single tool is listed.

The shipped policy (`policies/enterprise-v0.yaml`) lists three servers as its sinks, so the shipped
testbed built, and the container check of 24 November passed on it.

## Why

The label for a single tool (`ec29032`, 24 November) put `ticketing/reply_ticket` into the default
sinks of a testbed that labels it. The check in `compose.initial_policy` runs when a testbed names a
policy file, on the file laid over the default, and it still accepted names of servers only. The
guards read `server/tool` correctly; only the build refused it.

No test built a testbed with a tool label and a policy file other than the shipped one, and the
note of 24 November did not ask for one.

## The correction

A name in `sources` or `sinks` is known when it is

- a server of the testbed, or
- `server/tool` for a server of the testbed.

**The tool's own name is not checked at build.** A build has no list of the tools a server offers:
the server gives that list when it runs, and `mcl smoke` reads it there (that is where a wrong name
in `tool_labels` fails). The one list the build has is `tool_labels`, and checking against it would
refuse a policy that makes a sink of a tool the testbed does not label, which the guards read and
which is a policy's business: the label says how a call is scored, the policy what a guard watches.
So a misspelled tool on a known server builds, and the guard then watches a tool that does not
exist. `mcl smoke` could check a policy's tools against the server's list as it does for labels.
That is not built here: this change corrects a check and adds nothing.

A name with nothing after the `/` is refused. A server id holds no `/`, so the server is what
stands before the first one.

The error names servers and tools apart:

```
gateway.policy: unknown servers ['pastebin']; tools on unknown servers ['mail/read', 'mail/send']
```

An unknown server alone gives the sentence it gave before.

Two things about the lab that this run made visible. Neither is changed here.

- **A policy file is laid over the default policy.** So the policy at the gateway always has
  `sources` and `sinks`, also for a plugin guard whose policy file sets neither, and such a guard's
  own defaults for the two never apply. The default sources are the private and the mixed servers.
- **A list comes back as several JSON objects.** A server tool that returns a list
  (`crm.get_settings`, `crm.list_contracts`) answers with one JSON object per item, one after
  another, each over several lines. `tests/benchmark/reference.py` writes the same answer as one
  JSON list on one line. A guard or a detector that parses an answer therefore sees another shape
  in the Layer-1 reference flows than at the gateway. For a tool that returns one object
  (`get_customer`, `get_contract`) the two differ in line breaks only.
